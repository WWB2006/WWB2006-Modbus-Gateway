# 部署与运维

本文对应 README 路线表的**阶段 11**：把网关从「开发机上能跑」变成
「现场服务器上能长期稳定跑」。内容分四块：构建产物、安装、systemd 托管、日常运维。

---

## 1. 构建产物一览

`cmake --build build-linux` 之后，`build-linux/src/` 下会出现这些可执行文件。
理解它们的分工比记住名字重要：

| 产物 | 依赖 Qt | 用途 | 部署到现场 |
| --- | --- | --- | --- |
| `gateway_daemon` | **否** | 常驻采集，无界面。**这是生产环境要跑的那个** | ✅ |
| `slave_simulator` | **否** | 从站模拟器，用来在没有真实设备时验证链路 | 可选（调试用） |
| `gateway_cli` | 否 | 协议层自检，打印一条请求的组帧结果 | ❌ |
| `modbus_gateway` | 是（Widgets） | 图形界面，现场调试与巡检用 | 可选（工程师笔记本上） |

**关键点**：`gateway_daemon` 与 `slave_simulator` 完全不依赖 Qt。
服务器上不需要装 Qt 运行时 —— 这是把它们与界面程序分开编译的原因。
`gateway_daemon` 使用自研的 `NativeTcpTransport`（阻塞 socket + `select` 轮询），
而不是 Qt 的 `QTcpSocket`，因此也不依赖 Qt 事件循环。

> 验证这一点：在一台**没装 Qt** 的机器上执行
> `cmake -S . -B build -G Ninja && cmake --build build`，
> `gateway_daemon` 与 `slave_simulator` 应当照常生成。

## 2. 安装

### 2.1 目录约定

```
/opt/modbus-gateway/bin/gateway_daemon      # 程序
/etc/modbus-gateway/gateway.json            # 配置
/var/lib/modbus-gateway/records.db          # 数据库
/var/log/modbus-gateway/                    # 导出文件
```

### 2.2 步骤

```bash
# 1) 建用户。不给登录 shell —— 它只是个服务账号。
sudo useradd --system --no-create-home --shell /usr/sbin/nologin modbus

# 2) 建目录并授权
sudo install -d -o modbus -g modbus /opt/modbus-gateway/bin
sudo install -d -o modbus -g modbus /etc/modbus-gateway
sudo install -d -o modbus -g modbus /var/lib/modbus-gateway
sudo install -d -o modbus -g modbus /var/log/modbus-gateway

# 3) 放程序
sudo install -m 0755 build-linux/src/gateway_daemon /opt/modbus-gateway/bin/

# 4) 放配置（先从仓库的示例改起）
sudo install -m 0644 config/gateway.json /etc/modbus-gateway/gateway.json
sudo -u modbus nano /etc/modbus-gateway/gateway.json

# 5) 装 systemd unit
sudo install -m 0644 deploy/gateway-daemon.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now modbus-gateway
```

### 2.3 先做一次 dry-run

在真正托管之前，**一定要先手工跑一次 `--dry-run`**。它会把解析后的配置、
每台设备的链路可用性、数据库路径全部打印出来，但不采集：

```bash
/opt/modbus-gateway/bin/gateway_daemon /etc/modbus-gateway/gateway.json --dry-run
```

典型输出（下面这份来自**未启用 Qt SerialPort** 的构建，所以 `meter-02` 报不可用；
在装了 `libqt6serialport6-dev` 的 Linux 构建里不会有这一行）：

```
Modbus 网关常驻采集进程
  配置文件  : /etc/modbus-gateway/gateway.json
  数据库    : /var/lib/modbus-gateway/records.db（批量 500）
  设备      : 3 台
    - plc-01       tcp  轮询 500ms 超时 1000ms 重试 3 次 点位 1 个
    - meter-02     rtu  轮询 1000ms 超时 1000ms 重试 3 次 点位 1 个
    - vfd-03       tcp  轮询 2000ms 超时 1000ms 重试 2 次 点位 2 个
  日志等级  : info（单文件上限 32 MB）
  [不可用] meter-02：当前构建不支持 rtu 链路
有设备链路不可用。确认后可用 --dry-run 只做配置检查。

--dry-run：配置解析完成，未进行采集。
```

> 注意 `--dry-run` 在有设备不可用时**退出码为 1**（可用时是 0）。
> 这样 CI 与部署脚本可以用 `|| exit 1` 直接拦住"配置与现场不匹配"的部署。

看到 `[不可用]` 就是配置与现场不匹配，**先解决再启动服务**。
最常见的是串口：`rtu` 链路需要构建时带 Qt SerialPort 模块，
且设备节点要存在（`ls /dev/ttyUSB*`）且当前用户有权限（`dialout` 组）。

## 3. systemd 托管

`deploy/gateway-daemon.service` 里几处刻意的选择，改之前请先读这一段：

| 配置 | 值 | 为什么 |
| --- | --- | --- |
| `KillSignal` | `SIGTERM` | 网关收到 SIGTERM 会**优雅退出**：停轮询 → flush 未落盘数据 → 关库。改成 `SIGKILL` 会丢掉最后一批缓冲样本（最多 `batchSize` 条）。 |
| `TimeoutStopSec` | `20` | 给落盘留时间。数据库在机械盘上时，一次 500 条的 flush 可能到百毫秒级。 |
| `Restart` | `on-failure` | 断线由网关自己重连（进程不需要重启）；进程级崩溃（库文件被删、内存耗尽）才需要 systemd 拉起。正常退出不重启。 |
| `After=network-online.target` | — | 早于网络启动会白走一轮重连退避。能自愈，但日志会很难看。 |
| `RestrictAddressFamilies` | 含 `AF_NETLINK` | **不要删掉 `AF_NETLINK`**：`getaddrinfo` 在部分 glibc 版本上要用它，删了之后用主机名（而不是 IP）配的设备会解析失败。 |
| `ProtectSystem=strict` | — | 整个文件系统只读，只有 `ReadWritePaths` 列出的两个目录可写。 |

### 常用操作

```bash
sudo systemctl status modbus-gateway      # 看状态
sudo journalctl -u modbus-gateway -f      # 实时日志
sudo journalctl -u modbus-gateway --since "1 hour ago"
sudo systemctl restart modbus-gateway     # 改完配置后重启
sudo systemctl stop modbus-gateway        # 停止（会优雅落盘）
```

## 4. 日常运维

### 4.1 优雅退出与数据完整性

网关的退出顺序是固定的，也是它「不丢数据」的依据：

```
收到 SIGTERM/SIGINT
  → manager.stopAll()      停止轮询与重连，此后不会再有新样本
  → storage.flush()        把批缓冲里的样本一次性提交
  → storage.close()        关闭数据库
```

`stopAll()` 必须在 `flush()` **之前**，否则「落盘的内容」不等于「采集到的内容」——
这是最容易写反的一处。

### 4.2 手工触发一次退出（不改配置）

`--seconds N` 适合脚本化场景（端到端测试与 CI 用它）：

```bash
gateway_daemon /etc/modbus-gateway/gateway.json --seconds 30 --quiet
```

`--stop-file <路径>` 适合「让正在跑的服务收工」：该文件一出现即优雅退出。

```bash
touch /tmp/gateway.stop     # 服务会在下一轮循环（≤50ms）内退出
```

### 4.3 导出数据给同事

```bash
gateway_daemon /etc/modbus-gateway/gateway.json \
    --db /var/lib/modbus-gateway/records.db \
    --export-csv /var/log/modbus-gateway/export.csv \
    --seconds 1 --quiet
```

导出的是**库里现有的全部样本**（不只是本次进程采集的），列顺序固定为
`timestamp_ms,device,address,value,function,valid,note`，Excel 可直接打开。
注意 `note` 字段做了引号转义，因此不能用「按逗号切分」的方式解析。

### 4.4 数据库维护

数据库是标准 SQLite（WAL 模式）。可以随时用 `sqlite3` 命令查询：

```bash
sqlite3 /var/lib/modbus-gateway/records.db \
  "SELECT device, COUNT(*), MIN(ts_ms), MAX(ts_ms) FROM samples GROUP BY device;"
```

> **不要在对服务运行中的库执行 `VACUUM`**：WAL 模式下它会长时间持有写锁，
> 让采集侧写入失败。需要收缩体积时先 `systemctl stop`，VACUUM 完再启动。

长期运行后按时间清理旧数据：

```bash
sqlite3 /var/lib/modbus-gateway/records.db \
  "DELETE FROM samples WHERE ts_ms < (strftime('%s','now','-30 days')*1000);"
```

删除后空间不会立刻还给文件系统（SQLite 复用已分配的页），这是正常的。

### 4.5 指标怎么看

进程每 5 秒打印一次指标（`--quiet` 可关）。退出时会打印完整统计：

```
窗口 1000 次（上限 1000）
累计请求 812 / 成功 810 / 超时 2 / 异常 0
成功率 99.8% / 超时率 0.2%
延迟 ms：P50 3 / P95 12 / P99 40 / 均值 5.3 / 范围 1-61
  plc-01       请求 812 / 响应 810 / 超时 2 / 重传 2 / 重连 0(尝试 0) / CRC 错 0 / 异常 0
```

几个判读要点：

- **成功率的分母是窗口内样本数**，不是开机以来的总数。它反映「现在稳不稳」，
  不会被几小时前的正常状态稀释。
- **超时样本不计入延迟分位数**。超时的延迟等于超时阈值，把它算进去会让
  P95 永远等于阈值，看不出真实的性能分布。
- **`重传` 与 `重连` 是两件事**：重传是同一事务超时后重发（链路还活着），
  重连是链路断了在按退避策略重连。两者都持续增长说明线路质量有问题。

## 5. 故障排查

| 现象 | 最可能的原因 | 怎么确认 |
| --- | --- | --- |
| 启动后一直 `链路断开 / 正在重连` | 设备 IP/端口不对，或设备没上电 | `--dry-run` 看配置；`nc -vz <ip> <port>` 手工试连 |
| 日志刷 `超时`，`重传` 也在涨 | 超时阈值太小，或现场线路有丢包 | 看 `P95 延迟` 是否接近 `timeoutMs`；接近就把 `timeoutMs` 调大 |
| 有 `异常响应`（异常码非 0） | 地址/数量越界，或功能码不被设备支持 | 对照设备的寄存器手册核对 `points` 的 `func/address/count` |
| `[不可用] ... 不支持 rtu 链路` | 构建时没启用 Qt SerialPort | 重装 `libqt6serialport6-dev` 后重新 cmake |
| 数据库没有新数据 | 盘满、权限不足、或目录不存在 | `df -h`；`journalctl` 里搜「打开数据库失败」 |
| `--export-csv` 导出的是空文件 | 时间范围上界传成了 uint64 最大值（会被当成负数） | 本仓库已修（用 int64 上界），确认用的是最新版本 |
| 服务起来就退出，`Restart` 不断触发 | 配置文件语法错误 | `journalctl` 里搜「配置读取失败」，会带行列号 |

排查时优先看 `--dry-run` 的输出与 `journalctl` 的头 20 行 ——
网关在启动阶段把「配置解析结果、每台设备链路是否可用、数据库是否就绪」
都打印出来了，绝大多数问题在这一段就已经说明白了。
