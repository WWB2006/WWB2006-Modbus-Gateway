## 一 运行环境要求

### 1.1 操作系统

| 平台              | 支持情况     | 说明                                                  |
| --------------- | -------- | --------------------------------------------------- |
| Windows 10 / 11 | **已实测**  | 本文所有实测数据来自 Windows + Git Bash                       |
| Linux（Ubuntu）   | 支持，未实测   | `scripts/build_linux.sh` 为 Ubuntu 准备；模拟器用 POSIX 套接字 |
| WSL             | 支持，未实测   | 与 Linux 同路径                                         |
| macOS           | 理论可行，未验证 | 代码无平台特有依赖，但未提供脚本                                    |

从站模拟器刻意只用 **POSIX / WinSock 套接字**，不依赖 Qt、不依赖 epoll 等平台特性，  
因此 Windows 与 Linux 都能编译运行；Windows 下 CMake 会自动链接 `ws2_32`。

### 1.2 编译器与构建工具（含版本）

| 工具      | 最低要求                           | 本机实测版本                  | 是否必需          |
| ------- | ------------------------------ | ----------------------- | ------------- |
| C++ 编译器 | 支持 C++17                       | **Windows：MinGW-W64 g++ 8.1.0** / **Ubuntu 22.04：GNU 11.4.0** | **必需**        |
| CMake   | 3.16（`cmake_minimum_required`） | Windows **4.4.4**（在 Python venv 内，PATH 可见）/ Ubuntu **3.22.1** | 仅方式三 / 完整构建需要 |
| Git     | 任意                             | 有                       | 仅克隆仓库需要       |
| Python  | 3.x                            | **3.13.14**             | 仅交叉验证需要       |

支持的编译器：`g++` / `clang++` / `cl`（MSVC 走 `CMakeLists.txt` 里的 `/utf-8 /W4` 分支）。  
非 MSVC 编译器统一加 `-Wall -Wextra`，**本项目要求零告警**。

`CXX` 环境变量可指定编译器，两个构建脚本都会读取它：

```bash
CXX=clang++ ./scripts/build_portable_tests.sh
```

### 1.3 依赖库

**核心库 `gateway_core` 不依赖任何第三方库**，这是本项目的核心设计决定。

| 依赖                | 性质          | 何时需要                       | 说明                         |
| ----------------- | ----------- | -------------------------- | -------------------------- |
| C++ 标准库           | 必需          | 始终                         | `gateway_core` 唯一依赖        |
| `ws2_32`（Windows） | 必需（Windows） | 始终                         | 模拟器用 WinSock；CMake 与脚本自动链接 |
| **Qt 6.2+**       | **可选**      | 仅当需要 TCP 链路 / 界面 / Qt Test | 见下表                        |
| `pymodbus`        | 可选          | 仅交叉验证                      | 独立第三方实现，用于验证字节序            |
| pytest            | **不需要**     | —                          | 见文末「发现的一处表述不一致」            |

Qt 各组件的用途（顶层 `CMakeLists.txt` 用 `OPTIONAL_COMPONENTS` 声明，缺了不会导致配置失败）：

| Qt 组件                          | 用途                         | 阶段    |
| ------------------------------ | -------------------------- | ----- |
| `Core`                         | 基础（AUTOMOC 开启条件）           | 0     |
| `Network`                      | `TcpTransport`（QTcpSocket） | 2     |
| `Test`                         | `tests/unit/` 的 Qt Test 用例 | 1     |
| `Widgets`                      | 界面程序 `modbus_gateway`      | 5     |
| `SerialPort`                   | 串口 RTU                     | 4     |
| `SerialBus` / `Sql` / `Charts` | 规划中                        | 6 / 7 |

> **关键设计**：Qt 缺席时，顶层 CMake 只构建 `gateway_core` + `gateway_cli` + `slave_simulator`，  
> `ctest` 仍能跑三套可移植测试。协议层与设备层不持有线程、不读系统时间、不碰网络，  
> 所以能在没有图形环境的机器上完成全部核心验证。

### 1.4 配置项

#### `config/gateway.json` —— 设备与轮询配置

| 字段                                              | 类型                     | 默认值                       | 说明                             |
| ----------------------------------------------- | ---------------------- | ------------------------- | ------------------------------ |
| `name`                                          | string                 | —                         | 设备名，回调里用它区分数据来源                |
| `transport`                                     | `"tcp"` / `"rtu"`      | `"tcp"`                   | 链路类型，同时决定用 MBAP 还是 CRC 组帧      |
| `host` / `port`                                 | string / int           | `127.0.0.1` / `502`       | TCP 专用                         |
| `connectTimeoutMs`                              | int                    | `3000`                    | TCP 连接超时                       |
| `serialPort`                                    | string                 | `COM11`                   | RTU 专用（阶段 4）                   |
| `baudRate` / `parity` / `dataBits` / `stopBits` | int / char / int / int | `9600` / `N` / `8` / `1`  | RTU 专用                         |
| `unitId`                                        | int                    | `1`                       | 从站地址                           |
| `timeoutMs`                                     | int                    | `1000`                    | 单次响应超时；超时后重传                   |
| `retry`                                         | int                    | `3`                       | 最多重传次数，**总尝试次数 = `retry + 1`** |
| `pollIntervalMs`                                | int                    | `500`                     | 两次轮询之间的最小间隔                    |
| `points[].func`                                 | int                    | `0x03`                    | 支持 `3` / `4` / `6`             |
| `points[].address`                              | int                    | `0`                       | 起始地址（**协议地址，不是手册 40001 口径**）   |
| `points[].count`                                | int                    | `10`                      | 读多少个寄存器；**写单寄存器时恒为 1，不表示写入值**  |
| `points[].value`                                | int                    | `0`                       | 仅 `func = 6` 使用，表示要写进设备的数值     |
| `storage.database` / `storage.batchSize`        | string / int           | `data/records.db` / `500` | 阶段 6                           |
| `logging.level` / `logging.rotateSizeMb`        | string / int           | `info` / `32`             | 阶段 6+                          |

> **易错点**：写单寄存器时 `count`（读多少个）与 `value`（写什么）语义完全不同，  
> 代码里分别存在 `PollPoint::count` 与 `PollPoint::value`，不能互相替代。

#### `config/slave-simulator.json` —— 从站模拟器配置

| 字段                                          | 类型        | 默认值         | 说明                       |
| ------------------------------------------- | --------- | ----------- | ------------------------ |
| `simulator.bindAddress`                     | string    | `127.0.0.1` | 监听地址                     |
| `simulator.port`                            | int       | `5020`      | 监听端口（避免与真实 502 冲突）       |
| `simulator.unitId`                          | int       | `1`         | 本从站地址，其它地址的请求一律沉默        |
| `simulator.supportBroadcast`                | bool      | `false`     | 是否响应广播（地址 0）             |
| `simulator.verbose`                         | bool      | `true`      | 是否逐条打印请求                 |
| `registers.holding.size` / `.values`        | int / map | `128` / 见文件 | 保持寄存器区大小与初值              |
| `registers.input.size` / `.values`          | int / map | `64` / 见文件  | 输入寄存器区                   |
| `registers.coils.size` / `.values`          | int / map | `64` / 见文件  | 线圈区（值为 `true` / `false`） |
| `registers.discreteInputs.size` / `.values` | int / map | `32` / 见文件  | 离散输入区                    |

> **初值越界直接报错**：`values` 里出现超过 `size` 的地址时，配置加载会失败并给出定位，  
> 而不是静默丢弃——这是为了让脚本化构造边界场景时能立刻发现配置写错。

#### 从站模拟器命令行参数

```bash
./build_portable/slave_simulator [配置文件] [--port N] [--unit N] [--quiet]
```

| 参数         | 说明               |
| ---------- | ---------------- |
| 位置参数（可选）   | 配置文件路径，缺省用内置默认配置 |
| `--port N` | 覆盖监听端口           |
| `--unit N` | 覆盖从站地址           |
| `--quiet`  | 不逐条打印请求（脚本化测试用）  |

## 二 前置条件与准备步骤

### 2.1 路径 A：只验证核心（不装 Qt，**推荐先走这条**）

前置条件：一个 C++17 编译器。**不需要 Qt、不需要 CMake、不需要 Python。**

```bash
git clone <仓库地址> && cd MyselfModbusGateway

# Linux / WSL / Git Bash
./scripts/build_portable_tests.sh

# Windows PowerShell
.\scripts\build_portable_tests.ps1
```

脚本会做四件事：编译 5 个可执行文件 → 依次运行 `portable_tests`、`device_tests`、  
`simulator_tests`，任一步失败即中断（`set -euo pipefail` / `$ErrorActionPreference = "Stop"`）。

产物落在 `build_portable/`（已被 `.gitignore` 覆盖，不会误提交）。

### 2.2 路径 B：完整构建（装 Qt 6）

前置条件：Qt 6.2+、CMake 3.16+、与 Qt 匹配的编译器（MinGW 配 MinGW，MSVC 配 MSVC）。

```bash
# Ubuntu：需要 qt6-base-dev cmake g++
sudo apt install qt6-base-dev cmake g++
./scripts/build_linux.sh            # 默认 build-linux 目录

# Windows
.\scripts\build_windows.ps1 -QtPrefix "C:/Qt/6.8.0/mingw_64"
```

> **注意**：Qt 与编译器的位数和 ABI 必须匹配。用 MinGW 版 Qt 就必须用 MinGW 编译器，  
> 否则会在链接期报一堆 `undefined reference`。`build_windows.ps1` 的 `-QtPrefix`  
> 默认值是 `C:/Qt/6.5.3/mingw_64`，与实际安装路径不符时**必须显式指定**。

#### 2.2.1 Linux（Ubuntu / Debian）完整安装指令

**最小可用（够跑项目二当前全部功能）**——协议层、设备层、从站模拟器都用不到 Qt，
Qt 只用于 `TcpTransport`（Network）与 `tests/unit` 的 Qt Test：

```bash
sudo apt update
sudo apt install -y \
    build-essential \
    cmake \
    qt6-base-dev \
    libqt6test6 \
    qt6-base-dev-tools
```

| 包 | 提供什么 | 本项目哪里用到 |
| --- | --- | --- |
| `build-essential` | g++ / make / libc 头文件 | 编译核心库 |
| `cmake` | CMake ≥ 3.16 | 构建系统 |
| `qt6-base-dev` | Qt6 **Core / Gui / Widgets / Network / Sql** + `moc`/`uic`/`rcc` | `TcpTransport`、界面、`ctest` 识别 Qt6 |
| `libqt6test6` | Qt Test 运行库 | `tests/unit/tst_crc16.cpp`、`tst_codec.cpp` |
| `qt6-base-dev-tools` | `qmake6` 等工具 | 部分环境需要，装了更省事 |

**可选模块（按阶段需要再加）**：

| 包 | 提供什么 | 何时需要 |
| --- | --- | --- |
| `libqt6serialport6-dev` | Qt6 SerialPort | **阶段 4**：串口 RTU（`QSerialPort`） |
| `libqt6serialbus6-dev` | Qt6 SerialBus | 阶段 4 备选：Modbus 协议栈（若改用 Qt 自带实现） |

| `libqt6sql6-sqlite` | SQLite 驱动 | **阶段 6**：数据归档（注意是 `libqt6sql6-sqlite`，不是 `sqlite3`） |

一条命令装齐（含全部可选模块）：

```bash
sudo apt install -y \
    build-essential cmake \
    qt6-base-dev libqt6test6 qt6-base-dev-tools \
    libqt6serialport6-dev libqt6serialbus6-dev libqt6charts6-dev \
    libqt6sql6-sqlite
```

> ⚠️ **包名格式陷阱（实测踩过）**：Ubuntu 22.04（jammy）的 Qt6 模块开发包一律叫
> **`libqt6<模块名>6-dev`**，**不是** `qt6-<模块名>-dev`（后者是 24.04+ 才有的别名）。
> 写错会直接报 `E: 无法定位软件包`。对照表：
>
> | 想装 | 22.04 正确包名 | ❌ 错误写法 |
> | --- | --- | --- |
> | SerialPort | `libqt6serialport6-dev` | `qt6-serialport-dev` |
> | SerialBus | `libqt6serialbus6-dev` | `qt6-serialbus-dev` |
> | Charts | `libqt6charts6-dev` | `qt6-charts-dev` |
>
> 只有 `qt6-base-dev` / `qt6-base-dev-tools` 例外（base 模块用 `qt6-` 前缀）。
> 不确定时用 `apt search libqt6<关键词>` 或 `apt-cache search qt6 | grep <关键词>` 反查。

**额外工具（可选，非必需）**：

```bash
# 串口 RTU 阶段用：虚拟串口对（Linux 对应 Windows 的 com0com）

# 手工验证 Modbus 主站（命令行；Windows 对应 QModMaster 图形化工具）
# 注意：mbpoll 不在 Ubuntu 官方源，需从作者仓库安装
sudo add-apt-repository -y ppa:epsilonrt/mbpoll && sudo apt update
sudo apt install -y mbpoll
```

**交叉验证（pymodbus）**——不要用 `sudo pip`。Ubuntu 22.04 的 Python 3.10 也可能触发
PEP 668（`externally-managed-environment`），统一走 venv：

```bash
sudo apt install -y python3-venv
python3 -m venv .venv
source .venv/bin/activate
pip install pymodbus
```

然后按第 3.4 节的流程跑 `python scripts/verify_simulator.py`。

**一次跑通的完整流程**：

```bash
cd MyselfModbusGateway

# ① 三套可移植测试（不需要 Qt，先确认环境没问题）
./scripts/build_portable_tests.sh

# ② 完整构建 + ctest（此时含 Qt Test）
./scripts/build_linux.sh

# ③ 交叉验证
./build_portable/slave_simulator config/slave-simulator.json --quiet &   # 后台启动

```

**改了 `CMakeLists.txt` 之后必须删构建目录**，否则会继续用旧的缓存结果：

```bash
rm -rf build-linux        # build_linux.sh 的默认目录名就是 build-linux
./scripts/build_linux.sh
```

> ⚠️ **`build_linux.sh` 的构建目录叫 `build-linux`，不是 `build`。**
> `rm -rf build` 删不到它，缓存不重建，改完 `CMakeLists.txt` 也会报和上次一样的错。
> （2026-10-13 实测踩过：删了 `build` 后重跑，报错行号仍是旧的 `CMakeLists.txt:25`。）
>
> **另一个判据**：报错里的**行号**能证明文件到底换没换。若报错行号与改动后的源码
> 对不上，说明跑的还是旧文件——此时删多少次缓存都没用。

### 3.1 阶段 0：工程骨架

**测试代码**：无专门用例文件。这一阶段的「测试」是**构建系统本身能不能跑通**。

**测试方法**：

| 验证项                     | 命令                             | 期望输出                                       |
| ----------------------- | ------------------------------ | ------------------------------------------ |
| 顶层 CMake 可配置（无 Qt 也不报错） | `cmake -B build`               | 打印「未找到 Qt6：只构建 gateway_core 与 gateway_cli」 |
| 核心库可编译                  | `cmake --build build`          | 生成 `gateway_core` 静态库                      |
| CLI 可运行                 | `./build_portable/gateway_cli` | 见下方期望输出                                    |

**如何判断符合预期**——`gateway_cli` 的输出可**手工核对字节**：

```
modbus-gateway cli（阶段 0-1：协议层）

读保持寄存器 0 起 10 个
  PDU      : 03 00 00 00 0A
  TCP 请求 : 00 01 00 00 00 06 01 03 00 00 00 0A
  RTU 请求 : 01 03 00 00 00 0A C5 CD

解析 RTU 响应 01 03 04 00 0A 00 14 DA 3E
  寄存器[0] = 10
  寄存器[1] = 20

异常响应 01 83 02 C0 F1
  寄存器地址越界或地址口径不一致（40001 与 0-based 差一位）
```

三个可手算的核对点：

1. **MBAP 长度字段 = 6**，不是整帧长度 12（`00 01 00 00 | 00 06 | 01 | 03 00 00 00 0A`）。
2. **RTU CRC 低字节在前**：`C5 CD`（CRC16 值本身是 `0xCDC5`）。
3. **异常功能码 = 0x83** = `0x03 | 0x80`，异常码 `0x02`。

> Windows 控制台中文乱码的处理：`gateway_cli` 已调用 `SetConsoleOutputCP(CP_UTF8)`。  
> 若仍乱码，用 `chcp 65001` 切到 UTF-8 代码页。

**测试工具 / 方法**：**假链路（Fake Object）驱动**，这是本阶段最关键的方法选择。

`FakeSlaveTransport` 实现 `TransportInterface`，提供七个「脚本开关」，把现场故障变成可复现的开关：

| 开关                             | 模拟的现场故障       |
| ------------------------------ | ------------- |
| `setResponding(false)`         | 设备离线（收到请求不回应） |
| `setCorruptCrc(true)`          | 电磁干扰导致 CRC 出错 |
| `setFragment(true)`            | 半包（响应被拆成两段到达） |
| `setExceptionCode(code)`       | 从站返回异常码       |
| `setResponseUnitId(id)`        | 响应来自别的从站      |
| `setResponseTransactionId(id)` | 迟到 / 错配响应     |
| `setRegister(i, v)`            | 从站侧数据变化       |

**两个刻意的设计**（写进代码注释，是踩坑后的结论）：

1. **响应先进发件箱，由测试显式 `deliverNext()` 投递**，不在 `send()` 里同步回调。  
   原因：同步回调会在 `sendPending()` 还没写完 `attempts` / `deadline` 时就把事务解掉，  
   制造**状态再入**问题——这个 bug 是真实出现过的。
2. **`attach(transport)` 把「设置链路」与「接管字节回调」合成一个动作**。  
   原因：最初只调 `setTransport()` 会漏接线，表现为「请求发出但永远没有响应」，  
   这类遗漏靠 API 设计消除，而不是靠文档提醒。

```bash
# 结果：全部通过
```

除总量外，建议重点核对这几条**边界值**（它们是设计的核心约束，改代码时最容易破坏）：

| 断言                                | 期望                                     |
| --------------------------------- | -------------------------------------- |
| 99ms 不重传 / 100ms 重传               | 超时判定精确到 `timeoutMs`，不多不少               |
| 重传次数 = `retry` 配置；达到上限**只回调一次超时** | 不能重复上报                                 |
| 坏 CRC 帧的错误计数 = **1**（不是逐字节重复计数）   | 整帧丢弃，靠 `DecodeResult::frameLengthHint` |
| 在途期间第二个请求被拒绝，逻辑请求数仍为 1            | 单在途事务约束                                |
| 0x06 点位写入的是 `value` 而不是 `count`   | 字段语义不能混                                |
| 未支持的功能码被跳过且**不阻塞其它点位**            | 一个坏点位不能拖死整轮轮询                          |

**测试方法**：**闭环（round-trip）**，而不是「拿一串手写字节去对答案」。

```cpp
// simulator_tests.cpp 的核心辅助函数
ResponsePdu roundTrip(RegisterMap& map, uint8_t functionCode,
                      const std::vector<uint8_t>& pdu, ...) {
    RequestHandler handler(map);
    // 用主站侧编解码造请求帧 → 解帧 → 交给从站 → 返回响应 PDU
    const auto frame = encodeTcpRequest(transactionId, unitId, pdu);
    DecodeResult decoded;
    decodeTcp(frame.data(), frame.size(), decoded);
    return handler.handleRequest(decoded.frame);
}
```

为什么用闭环：手写字节只能验证「我认为对的」；闭环能验证「两边对同一个规范的理解一致」。  
代码注释里写得很直白——**「功能码 0x%02X 的请求帧无法解出，测试用例本身有问题」**，  
即用例失败时先怀疑用例，而不是产品代码。

#### 测试二：pymodbus 交叉验证（第三方独立实现）—— **不能省略**

**测试代码**：`scripts/verify_simulator.py`（212 行，54 项断言）

**测试工具**：`pymodbus`（本机实测 **3.15.0**），第三方独立实现。

**为什么必须做这一步**（`docs/阶段3验收记录.md` 引用的实现指导原文）：

> 模拟器自己实现了错的字节序，把主站也带偏，所以一定要用第三方工具交叉验证。

自研主站 + 自研从站的闭环测试只能证明**两边理解一致**；如果两边一起把字节序理解错了，  
测试依然全绿。pymodbus 读出的值与配置一致，才说明字节序、位打包顺序、异常码真的是对的。

**方法要点**：脚本用了两条不同的通道，因为 pymodbus 会**在客户端就挡掉非法请求**。

| 通道                           | 用途                   | 覆盖                                                                           |
| ---------------------------- | -------------------- | ---------------------------------------------------------------------------- |
| `ModbusTcpClient`（高层 API）    | 正常读写、异常路径            | 读 HR / IR / COIL / DI；写 HR(0x06) / HR(0x10) / COIL(0x05) / COIL(0x0F)；越界返回异常 |
| `raw_request()`（手写 socket 帧） | **绕过客户端校验**，测从站的拒绝行为 | 读 126 个 → 从站回 `83 03`；单元号 9 请求 → 从站沉默                                        |

`raw_request()` 的必要性：pymodbus 客户端自己就会拒绝 `count > 125`（抛 `ValueError`），  
走它**永远测不到从站收到非法帧会怎么回**——而现场真正的坏主站是会发这种帧的。

**如何判断符合预期**：

```bash
# 终端 1
./build_portable/slave_simulator config/slave-simulator.json
# 终端 2
python scripts/verify_simulator.py
# 断言 54 项，失败 0 项
# 结果：全部通过
```

若提示 `无法连接到 127.0.0.1:5020，请先启动 slave_simulator`，说明终端 1 没起来或端口被占，  
脚本会 `return 2`（**区别于断言失败的 `return 1`**，便于区分「环境没准备好」与「测出问题」）。

交叉验证里最关键的三条断言（字节序的最终证据）：

| 断言                    | 说明                             |
| --------------------- | ------------------------------ |
| `HR[4] == 65535`      | **全 1 边界**：字节序写反会变成 65535 以外的值 |
| `HR[0..11]` 与配置逐项一致   | 大端解析正确                         |
| `COIL[0..11]` 与配置逐项一致 | 位打包 LSB-first 正确               |

#### 观察到的现象（有价值，值得记住）

pymodbus 在客户端就挡掉了 `count > 125` 与 `count = 0`，抛 `ValueError` 而不是发出去。  
这说明**规范上限是各家实现的共识**，不只是本项目的自定约束——  
项目里的 `kMaxReadRegisters = 125`、`kMaxWriteRegisters = 123`、  
`kMaxReadBits = 2000`、`kMaxWriteBits = 1968`、`kMaxPduSize = 253` 与第三方一致，属交叉印证。

### 7.2 CMake 配置在 Ubuntu 上失败：`OPTIONAL_COMPONENTS` 里的 `SerialBus`（已修复）

**现象**（Ubuntu 22.04，Qt 6.2.4，CMake 3.22.1）：

```
CMake Error at .../Qt6SerialBusTools/Qt6SerialBusToolsTargets.cmake:86 (message):
  The imported target "Qt6::canbusutil" references the file
  "/usr/lib/qt6/bin/canbusutil" but this file does not exist.
Call Stack (most recent call first):
  .../Qt6/Qt6Config.cmake:219 (find_package)
  CMakeLists.txt:25 (find_package)
```

**两层原因叠加**：

1. **Ubuntu 打包缺陷**——`libqt6serialbus6-plugins` 提供了 `Qt6SerialBusTools` 的
   CMake 配置文件，却没附带 `/usr/lib/qt6/bin/canbusutil` 这个可执行文件。
   （不是我们装错了包，也不是 Qt 版本问题。）
2. **我们的 `CMakeLists.txt` 里列了一个从未使用的模块**——`OPTIONAL_COMPONENTS`
   中含 `SerialBus`，于是 `Qt6Config.cmake` 会去 `find_package(Qt6SerialBus)`，
   进而加载有缺陷的 `Qt6SerialBusTools`。

**关键认知**：`OPTIONAL_COMPONENTS` 这个名字有误导性——它只保证「**整个 Qt6 找不到时**
不把 `Qt6_FOUND` 置假」，对子模块自身 `find_package` 抛出的 `FATAL_ERROR` **没有保护作用**。

**已修**：`OPTIONAL_COMPONENTS` 由
`Widgets Network SerialPort SerialBus Sql Charts Test` 收敛为 `Widgets Network Test`。
依据是 grep 全仓库的实测结果——只有这四个组件真的被 target 链接：

| 组件 | 使用位置 |
| -- | -- |
| `Core` | 协议层 / 设备层基础类型 |
| `Network` | `src/transport/TcpTransport.cpp` |
| `Widgets` | `src/main.cpp` 的 `modbus_gateway` 界面程序 |
| `Test` | `tests/unit/` 的 `tst_crc16` / `tst_codec` |

`Sql` 从未使用；`SerialPort` / `SerialBus` / `Charts` 是阶段 4 / 7 才需要，
已把预留位置和原因写进 `CMakeLists.txt` 注释，**接入串口链路前不要再把它们加回来**。

> 附：同屏的 `Could NOT find OpenGL (missing: OPENGL_INCLUDE_DIR)` 只是 NOTICE 级，
> 全仓库无 target 链接 `Qt6::OpenGLWidgets`，不中断配置。仅在 `modbus_gateway`
> 链接阶段出现 `undefined reference to *gl*` 时才需补 `libgl-dev libglu1-mesa-dev`。

### 7.3 测试硬编码构建目录名，换构建路径必失败（已修复）

**现象**：`ctest` 下 `simulator_tests` 报「打不开配置文件：`build_portable/test_slave_config.json`」，
**断言 74 项 / 失败 4 项**（Windows 基线是 87 / 0）。

**根因**：`tests/portable/simulator_tests.cpp` 三处把临时配置路径写死成
`build_portable/test_slave_config*.json`，即**硬要求工作目录下存在 `build_portable/` 子目录**：

- `build_portable_tests.sh` 是 `cd` 到仓库根目录再跑的，`build_portable/` 真实存在 → **碰巧成功**；
- ctest 会 `changing into directory: .../build-linux`，那里没有该子目录 → **必失败**。

**被测功能没有 bug**：`loadSimulatorConfig` 报告「打不开」是完全正确的行为。
坏的是测试脚手架——源码第 394 行注释原写着「测试里不依赖工作目录」，
实现却硬依赖一个特定子目录，**注释与实现相反**。

**74 vs 87 的 13 项差异解释**（数字必须对得上，这是定位手段）：

| 来源                                            | 项数 |
| --------------------------------------------- | -- |
| 第 398 行 `check(file != nullptr)` FAIL         | +1 |
| 第 417 行 `check(ok, ...)` FAIL                 | +1 |
| `if (ok)` 为假 → 第 **419–434 行** 13 项断言被跳过 | −13 |
| **合计（87 → 74）**                              |    |

**已修**（两处，选这个方案是为了两条路径都不污染仓库）：

1. `simulator_tests.cpp`：3 处路径去掉 `build_portable/` 前缀，改为写**当前工作目录**；
   注释改成真实说明，并记录"曾经写成什么、为什么不行"。
2. `build_portable_tests.sh`：运行方式从仓库根目录 `./build_portable/xxx`
   改为子 shell 内 `( cd build_portable && ./xxx )`。

效果：ctest 下临时文件落 `build-linux/`，sh 下落 `build_portable/`，
**两者都已被 `.gitignore` 忽略**，既不失败也不让仓库根目录出现游离 json。
刻意不用 `<filesystem>`（MinGW g++ 8.1.0 需额外链 `-lstdc++fs`）、
不用 `#ifdef` 包裹的 `mkdir`、不传 CMake 宏——保持 `tests/` 零平台相关代码。

**Windows 侧复验结果**：`( cd build_portable && ./simulator_tests.exe )` → **87 项 / 0 失败**；
仓库根目录无游离 json；`git status` 干净。

**方法论结论**：**单一构建路径会掩盖测试基建缺陷。** 这个 bug 在 Windows 上潜伏多轮
（131/88/87 全绿）不是因为它不存在，而是因为只有一条构建路径、且路径恰好匹配。
判定口径：测试里出现**硬编码的构建目录名或工作目录假设**，就应当作 bug，
哪怕它当前是绿的。
