# 面试追问与简历攻防指南 (Technical Interview Cheatsheet)

本指南针对**上位机开发、工业软件工程师、测试开发工程师**三类求职方向的高频深度追问，提供原理级解答与项目落地佐证。

---

### Q1: Qt 信号与槽在跨线程传递数据时底层是怎么工作的？为什么不能用默认连接？
- **原理**：
  - `Qt::DirectConnection`：槽函数在**发射信号的线程**立即同步执行，相当于直接函数调用，若涉及跨线程操作 UI 对象会引发竞态甚至崩溃。
  - `Qt::QueuedConnection`：Qt 将信号参数序列化为 `QMetaCallEvent` 事件，压入目标接收对象所在线程的事件队列 (`QEventLoop`)。目标线程在下一次事件循环时调度执行槽函数。
- **本项目落点**：
  通信采集与数据库操作均在后台 `std::thread` 工作线程中执行，向主窗口传递 `CommunicationRecord` 时显式指定 `Qt::QueuedConnection` 或通过 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`，确保 UI 线程单线程访问控件，彻底避免多线程死锁或闪退。

### Q2: 讲讲 Modbus TCP 与 RTU 的核心差异？CRC-16 和多字节寄存器的大端字节序如何处理？
- **原理**：
  - **链路不同**：TCP 基于以太网，利用 7 字节 MBAP 报头（含事务号、协议号 0、长度、单元号），依赖 TCP/IP 自身的完整性校验，无需帧尾 CRC；RTU 基于串行链路（RS485/RS232），使用 1 字节从站地址 + PDU + 2 字节 CRC-16 校验码。
  - **CRC-16 字节序**：Modbus 规定 CRC-16 多项式为 `0xA001`，初值 `0xFFFF`，发送时**低字节在前，高字节在后**（Little-Endian）；
  - **数据寄存器字节序**：PDU 内的 16 位寄存器数值采用网络字节序，即**高字节在前，低字节在后**（Big-Endian）。
- **本项目落点**：
  `Crc16::compute` 采用 256 元素预计算表，`ModbusCodec` 严格按大端提取寄存器 `(high << 8) | low`，通过 `pymodbus` 官方参考实现交叉核验 100% 一致。

### Q3: 为什么断线重连不能使用固定间隔疯狂重试？指数退避与随机抖动 (Jitter) 的依据是什么？
- **原理**：
  - 若使用固定间隔（如每 500ms 重试一次），在大型工业现场当车间断电后恢复供电时，数十台甚至数百台网关和设备会同时发起 TCP SYN 握手，瞬间打满交换机队列并压垮从站 CPU，形成典型的**惊群效应与重试风暴 (Thundering Herd / Retry Storm)**。
  - **指数退避**将重试时间逐次翻倍（$1\text{s}, 2\text{s}, 4\text{s}, 8\text{s} \dots$ 封顶 $30\text{s}$），降低网络总吞吐压力。
  - **随机抖动 (Jitter)** 在计算出的退避基数上叠加 $0\% \sim 25\%$ 的随机偏移量，从统计学上将不同设备的并发重试脉冲彻底打散为均匀分布。
- **本项目落点**：
  `ReconnectPolicy` 实现了严格的指数退避与随机抖动，并在重试达到上限后截断，从站重启后网关在 1 个退避周期内平滑恢复。

### Q4: SQLite 默认写入为什么极慢？你是如何优化到 40 万条/秒的？
- **原理**：
  - 默认状态下 SQLite 处于 `DELETE/ROLLBACK` 日志模式，每次 `INSERT` 都是一个独立事务，每次提交都要执行一次操作系统的 `fsync` 刷盘操作，机械硬盘受物理寻道限制仅几十次/秒，SSD 也只有数百次/秒。
- **本项目四重优化**：
  1. **WAL 模式** (`PRAGMA journal_mode = WAL`)：改写只追加到预写日志，读操作与写操作互不加锁阻塞。
  2. **降低同步开销** (`PRAGMA synchronous = NORMAL`)：仅在检查点同步，速度提升数倍且保证系统断电不损坏。
  3. **扩大内存缓存** (`PRAGMA cache_size = -64000`)：预留 64MB 缓存，临时表走内存。
  4. **批量事务提交**：内存维护 500 条环形缓冲区，统一执行 `BEGIN TRANSACTION; ... COMMIT;`，将 500 次刷盘合为 1 次。
- **本项目实测数据**：
  `tests/unit/tst_storage` 实测写入 2000 条记录仅耗时 **4.56ms**，等效吞吐达 **437,905 条/秒**。

### Q5: 多台从站设备并发轮询时，如果某一从站网线拔掉超时，如何保证其他从站不受影响？
- **原理与实现**：
  传统简易网关常在同一个单线程循环中依次轮询 `dev1 -> dev2 -> dev3`。当 `dev2` 发生 1 秒超时或尝试重连时，整个轮询循环停滞，`dev3` 的周期严重拖尾。
- **本项目落点**：
  `PollScheduler` 采用**设备专属线程架构**：每台设备在独立的轻量级工作线程中运行私有定时器和状态机。`dev2` 超时进入退避休眠时，`dev1` 与 `dev3` 依然精确按 500ms 周期执行，互不阻塞，轮询抖动保持在 5% 以内。

### Q6: 为什么强调“协议编解码层与网络传输层解耦”？
- **设计价值**：
  1. **便于脱离硬件与网络进行纯单测**：`ModbusCodec` 仅接收原始字节数组并输出结构体，在 `tests/unit/tst_codec` 中无需启动 socket 或虚拟串口，毫秒级即可完成全部功能码的边界与回归测试。
  2. **协议复用**：TCP 与 RTU 核心均为 Modbus PDU，编解码器复用度达 90% 以上。
  3. **双平台无缝迁移**：当在 Linux 上编译无界面守护进程时，无需链接 Qt Widgets 即可直接复用全部核心协议库。

### Q7: 实时曲线显示如果持续运行 24 小时，数据点不断累积会导致界面越跑越卡，如何解决？
- **瓶颈分析**：
  如果每次来一个数据点就向图表 `QLineSeries` 无限 `append()`，当数据点达到数万个时，Qt 每次重绘遍历成千上万个折线点，造成 GPU/CPU 绘制卡死甚至内存溢出 (OOM)。
- **本项目优化**：
  1. **定长双端队列截断**：`ChartPanel` 内部采用定长环形队列，最多仅保留最近 200 个采样点，内存占用恒定。
  2. **刷新频率去抖 (Throttling)**：界面刷新由独立的 2Hz 刷新定时器触发，而不是每收到一个报文就重绘一次，彻底解耦网络到达率与 UI 渲染帧率。

### Q8: 怎么保证异常注入测试是“稳定可回归”的？
- **设计要点**：
  单纯的随手随机注入会导致单元测试时好时坏（Flaky Test）。本项目在 `FaultInjector` 中将异常策略配置化为 JSON 文件，并在自动化测试中使用固定的伪随机种子或确定性计数器（如 `afterRequests: 20`），确保每次 CI 运行断言结果 100% 稳定可复现。
