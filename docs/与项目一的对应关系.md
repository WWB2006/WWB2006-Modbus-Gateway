# 与项目一 MyselfWebServer 的对应关系

写这份文档的原因：两个项目解决的是**同一类工程问题**——「把字节流可靠地搬进应用层，
在并发与故障下保持正确」。技术栈不同，但设计判断可以互相印证。

面试时这一段很有用：面试官问你「项目二和项目一有什么关系」，你回答的不是「都是 C++ 项目」，
而是「同一个问题在两套技术栈里的两种解法，以及我为什么这样取舍」。

## 一 总对照表

| 能力 | 项目一 MyselfWebServer | 项目二 MyselfModbusGateway | 相同点 | 差异与取舍 |
| --- | --- | --- | --- | --- |
| 事件来源 | epoll(ET) + 自定义 EventLoop | Qt 事件循环 + QTcpSocket 信号槽 | 都是「事件驱动、非阻塞」 | 项目一自己管 epoll 与事件数组，项目二把这段交给 Qt；换来更少代码，代价是对底层不可控 |
| 连接抽象 | TcpConnection + Channel(weak_ptr 保活) | TransportInterface + DeviceSession | 都是「一条链路一个状态机」 | 项目二把「网络连接」放宽为「任何能收发字节的链路」，所以串口与测试替身能复用同一套上层代码 |
| 接收缓冲 | Buffer（readIndex_/writeIndex_ + retrieve） | ByteAccumulator（readIndex_ + consume） | 同一套「读指针 + 累积 + 消费」思路 | 项目一为 HTTP 做了 peek/retrieveAsString 等便利方法，项目二只需要切片给解码器 |
| 分帧依据 | HTTP：`\r\n\r\n` + Content-Length / chunked | Modbus TCP：MBAP 长度字段；Modbus RTU：功能码推断 + 静默间隔 | 都靠协议自带的边界信息，绝不「按一次 recv 当一帧」 | RTU 没有长度字段，必须知道方向才能推断帧长，所以解码函数拆成了请求/响应两个入口 |
| 半包 / 粘包 | HttpParser 保留解析状态，循环解析直到无完整报文 | DeviceSession::onBytes 循环 decode + consume | 完全相同的循环结构 | 项目二多一条「坏 CRC 时按推断帧长整体丢帧」的恢复路径 |
| 定时与超时 | TimerQueue + 把最近到期时间交给 epoll_wait 当超时值 | tick(nowMs) 由 QTimer（Qt）或假时钟（测试）驱动 | 都把时间抽象成外部输入，循环内不做阻塞等待 | 项目一的定时器跑在循环线程里天然无锁；项目二把时间显式传入，测试可以精确控制到毫秒 |
| 跨线程 | eventfd 唤醒 epoll_wait + runInLoop + 线程归属断言 | Qt::QueuedConnection + 工作线程（阶段 5、9） | 都禁止跨线程直接改状态，只投递任务 | 项目一用断言把「偶发崩溃」变成「立刻暴露」；项目二靠 Qt 的连接类型约束 |
| 过载与背压 | 连接数超限直接返回 503 | 单在途事务 + 重传上限 + 轮询间隔 | 都是「宁可明确拒绝，也不要堆积成雪崩」 | 项目一的背压作用在连接粒度，项目二作用在事务粒度 |
| 可观测性 | Prometheus：12 档延迟直方图、连接/请求/拒绝计数 | DeviceStats：请求/响应/超时/重传/CRC/异常/丢弃计数 | 都先把关键事件计数，再谈曲线 | 项目二的指标更偏「通信质量」，项目一更偏「服务容量」 |
| 日志 | AsyncLogging：前端零分配 + 双缓冲落盘 + 32MB 轮转 | util/Logger（阶段 7） | 都要求日志不阻塞主流程 | 项目二的日志还要能按设备名过滤，便于现场定位是哪台设备出问题 |
| 故障注入 | fault_injection.py：半包、粘包、慢连接、超长请求等 6 类 | 阶段 8：离线、坏 CRC、异常码、半包、粘包、乱序 6 类 | 都是「把偶发问题做成必现用例」 | 项目一的故障在协议栈层，项目二的故障还包括现场设备语义（异常码） |
| 测试 | GoogleTest 46 例 + pytest 15 例 | Qt Test + 可移植测试 131 + 88 例 | 都是「单元测试与接口测试两层」 | 项目二多了一层「不依赖框架的可移植测试」，装 Qt 之前就能验证核心 |
| CI | GitHub Actions：构建 + 单测 + 接口测试 | 同一套路（阶段 10 接入） | 提交即回归 | — |
| 架构决策 | ADR 0003 主从 Reactor、0004 定时器、0005 日志 | ADR 0001 分层与依赖方向、0002 时间与线程模型 | 都用 ADR 记录「为什么这样设计」 | — |
| 证据文档 | docs/bench（压测矩阵、火焰图、长稳数据） | docs/protocol-matrix.md（字节序与报文样例） | 都把「可复现的证据」放进仓库 | — |

## 二 三个「同一问题、两种解法」的细节

### 1. 半包与粘包

项目一：`TcpConnection` 收到可读事件后循环调用 `HttpParser::parse()`，缓冲区里没有完整报文就返回，
把中间状态留在解析器里。

项目二：`DeviceSession::onBytes()` 用同样的循环：

```cpp
while (accumulator_.size() > 0) {
    consumed = decodeTcp(accumulator_.data(), accumulator_.size(), decoded);
    if (consumed > 0) { accumulator_.consume(consumed); handleFrame(decoded.frame); continue; }
    if (decoded.status == DecodeStatus::Incomplete) return;   // 半包：等下一批
    ...
}
```

**差别在错误恢复**：HTTP 解析失败可以回 400 并关闭连接；Modbus RTU 的误码帧必须尽量丢弃后继续，
因为现场是长连接、周期轮询，一次误码不该让整条链路停下来。所以 `DecodeResult` 里加了
`frameLengthHint`，让上层能整帧丢弃而不是逐字节重新同步。

### 2. 超时从哪里来

项目一：把最近到期时间交给 `epoll_wait` 当超时值，定时任务天然在循环线程执行，不需要额外线程与锁。

项目二：设备层的 `tick(nowMs)` 完全不知道自己是被谁调用的——

```cpp
// Qt 侧（阶段 5 的界面与阶段 11 的无界面网关）
QTimer::singleShot / QTimer timer(20ms) → manager.tick(nowMs());
// 测试侧
session.tick(0); session.tick(100);   // 精确构造「刚好超时」的边界
```

这个取舍让「超时重传」这种最容易出错的逻辑变成了可重复验证的纯函数式流程：
临界值 99ms 不重传、100ms 重传，测试里各断言一次。

### 3. 一次只允许一个在途事务

项目一的背压是「连接数超过上限返回 503」；项目二的背压是「同一设备同时只允许一个在途事务」。
后者是 Modbus 的现实约束：RTU 链路上根本没有事务号，两条请求同时在飞就一定无法区分响应属于谁。
所以 `requestReadHoldingRegisters()` 在 `pending_.active` 时直接返回 false，而不是排队——
排队会让「当前值」变成「历史值」，对工业采集是错的。

## 三 面试时怎么把两个项目串起来

30 秒版：

> 我做过两个 C++ 项目，一个是 Linux 上基于 epoll 主从 Reactor 的 HTTP 服务器，
> 一个是 Qt 的 Modbus 工业网关。它们的共同点是都在解决「字节流怎么可靠地变成应用层对象」：
> 前者用自研的 Buffer 加 HTTP 状态机，后者用缓冲区加 Modbus 解码器，半包粘包的处理结构几乎一样。
> 区别在于，HTTP 那条链路我可以自己管 epoll，Modbus 这条链路我用 Qt 的事件循环换开发效率，
> 但把超时做成外部驱动的 tick，所以重传逻辑在没有硬件的情况下也能精确测出来。

可能的追问与答法：

| 追问 | 回答要点 |
| --- | --- |
| 两个项目的分帧有什么不同？ | HTTP 有 Content-Length 或 chunked，RTU 没有长度字段，只能靠功能码推断帧长或静默间隔，所以 RTU 解码必须区分请求与响应 |
| 为什么项目二不像项目一那样自己写 epoll？ | 工业上位机的瓶颈在设备响应和现场链路，不在单机事件循环；Qt 的封装足够，省下的时间投在协议与测试上更值 |
| 你在两个项目里都做了什么取舍？ | 项目一：ET 换性能，代价是必须循环读到 EAGAIN；项目二：用框架换开发效率，代价是底层不可控，所以把协议层做成不依赖框架的可移植内核 |
