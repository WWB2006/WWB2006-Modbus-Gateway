# ADR 0003：存储选 vendored SQLite，写入走批量事务

- 状态：接受
- 日期：2026-10-13

## 背景

阶段 6 要给采集数据找一个落地存储。约束有三条：

1. 现场一台机器要能连续跑，一秒几十个点，一天千万级写入；
2. 现场机器上不一定有数据库服务，运维也不该为了一个采集程序去装 MySQL；
3. 数据要能被同事用 Excel 打开、能用命令行查。

可选方案：

| 方案 | 问题 |
| --- | --- |
| 纯文本 / CSV 追加 | 查询要全表扫描；崩溃时最后一行可能是半行 |
| Qt SQL + SQLite | 把存储层绑上 Qt，而无界面网关恰恰要在没装 Qt 的机器上跑 |
| 系统 SQLite 库 | 版本漂移：不同发行版的 `libsqlite3` 版本与编译选项都不同，行为不一致 |
| MySQL / PostgreSQL | 为了一个采集程序装数据库服务，运维成本不成比例 |

## 决策

**vendored SQLite amalgamation**（`third_party/sqlite/sqlite3.c`，3.46.1）编进 `gateway_core`，
直接用 C API（不用 Qt SQL），并做三件事：

1. **批量事务**：样本先进内存缓冲，攒够 `batchSize`（默认 500）后在一个事务里提交，
   事务内复用同一条预编译语句；
2. **WAL + `synchronous=NORMAL`**：读写不互相阻塞，且不必每条都 fsync；
3. **主键 `(device, ts_ms, address)` + `INSERT OR REPLACE`**：重传导致的重复样本自动去重。

## 理由

1. **零外部依赖**：单文件源码随仓库走，任何平台编出来都一样。`git clone` 之后
   `cmake && make` 就能跑，不需要先解决"装哪个版本的 sqlite"；
2. **不绑 Qt**：用 C API 而非 Qt SQL，存储层因此能在无 Qt 的无界面网关里复用 ——
   而存储层恰恰是网关最需要的部分；
3. **批量是必须的，不是优化**：逐条 `INSERT` 每次都要 fsync，同样数据量下
   事务批量提交比逐条快两个数量级。这不是"性能调优"，是"能不能用"的区别；
4. **WAL 的取舍明确**：`synchronous=NORMAL` 在 WAL 下断电最多丢最后一个事务。
   对采集数据（本来就有周期性的下一批）这是可接受的，换来的是写入吞吐的大幅提升。

## 代价

1. 仓库多了一个 ~9MB 的 C 源文件。它必须由 **C 编译器** 编译（当 C++ 编会因
   `void*` 隐式转换、`sqlite3WhereTrace` 重定义等失败），因此项目要启用 C 语言；
2. 升级 SQLite 要手工替换文件。这是刻意的：升级应当是一次有意识的提交，
   而不是某次 `apt upgrade` 的副作用；
3. WAL 模式下会多出 `-wal` / `-shm` 两个文件。备份时不能只拷 `.db` ——
   这一点写进了运维文档。

## 与项目一的关系

项目一是内存型服务，不落盘，因此没有这个问题。两个项目在"依赖管理"上的判断相反：
项目一追求极致性能所以手写缓冲区、不引第三方；项目二追求**可部署性**所以把
依赖 vendored 进来、宁多一个源文件。取舍的依据是部署环境，不是技术偏好。
