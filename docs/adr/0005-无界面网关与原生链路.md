# ADR 0005：无界面网关自带原生链路，不依赖 Qt

- 状态：接受
- 日期：2026-10-15

## 背景

阶段 11 要交付 `gateway_daemon`：部署在服务器上、常驻采集、没有图形界面。
它需要一条 TCP 链路。

但已有的 `TcpTransport` 继承 `QObject`、用 `QTcpSocket` 与 Qt 事件循环。
`TransportFactory.cpp` 也 `#include "TcpTransport.h"`，因此**整个工厂翻译单元都依赖 Qt**。

于是出现一个两难：

- 网关若用 `TransportFactory`，就必须链 Qt Core + Qt Network。
  「不装 Qt 也能部署」这个卖点没了；
- 网关若不用工厂，就得自己 `new` 具体链路类型，等于把「用哪种链路」的知识复制一份，
  将来加第三条链路必然漏改一处。

还有第二个问题：Qt 链路靠事件循环投递字节，而网关的主循环是自己写的
（`while (!stop) { tick(); sleep(); }`）。没有事件循环，字节永远不会到达 `onBytes`。
即"链路能发不能收"。

## 决策

分两步。

**第一步：把"链路从哪来"抽象成一层可注册的表（`TransportRegistry`）。**

```cpp
void registerTransportBuilder(TransportKind kind, TransportBuilder builder,
                              TransportAvailability availability);
std::unique_ptr<TransportInterface> createRegisteredTransport(const TransportConfig&, std::string&);
bool isRegisteredTransportAvailable(TransportKind);
```

- `TransportRegistry.cpp` **不含任何 Qt 头文件**，任何构建都会编译它；
- `TransportFactory.cpp` 里的 Qt 实现通过一个文件级静态对象在 `main()` 之前自注册
  （用局部静态而不是全局对象，避免跨翻译单元的静态初始化顺序问题）。

**第二步：`gateway_daemon` 无条件注册并使用自研的 `NativeTcpTransport`。**

`NativeTcpTransport` 是阻塞 socket + `select` 轮询：带超时的非阻塞 connect
（连上后恢复阻塞）、`send` 直写、`pollOnce()` 用 `select` 超时 0 做纯轮询。

**第三步：给链路接口加一个主动驱动入口。**

```cpp
virtual void pump() {}   // TransportInterface，默认空实现
```

- Qt 链路继承默认的空实现（事件循环已经在投递字节）；
- `NativeTcpTransport` 覆写它，真正去读一次 socket；
- `DeviceSession::pump()` / `DeviceManager::pump()` 逐层转发。

网关主循环里的顺序是 `pump()` 然后 `tick()`，不能反 —— 反了会让"刚好在本轮到达的
响应"被当成本轮超时处理，白白多一次重传。

## 理由

1. **网关的行为不应取决于"这台机器恰好装没装 Qt"**。若按 Qt 有无切换实现，
   同一份 `gateway.json` 在两台机器上会走两套 socket 代码（异步信号槽 vs 主动轮询），
   一旦只在一边复现问题，排查成本极高。所以 daemon **固定**用原生链路；
2. **`pump()` 用显式接口而不是在 `isOpen()` 里顺手读一把**：后者会让一个查询函数
   产生副作用，调用方无法控制读取时机，"为什么这里会收到数据"变得不可追踪；
3. **注册表而非硬编码**：测试可以注册假链路、无 Qt 构建可以注册原生链路、
   Qt 构建自动注册 Qt 链路，三者互不干扰。

## 代价

1. 项目里有了**两套 TCP 实现**。它们会各自演化 —— 修了 Qt 版的一个 bug
   不会自动惠及 daemon。缓解办法是两者共用 `TransportInterface` 契约与
   `ByteAccumulator`，且 daemon 的链路有独立测试（见下）；
2. Qt 构建里的 daemon 不再用 `TcpTransport`，也就是说 Qt 版链路的问题
   在 daemon 上不会暴露。这是刻意的取舍：**一致性优先于复用**；
3. 串口链路仍然只有 Qt 实现。所以无 Qt 构建的 daemon 不支持 `rtu` 设备，
   会在启动时明确报 `[不可用]`（而不是静默跳过）——
   现场排查最怕"启动了但什么也没发生"。

## 验证

`tests/portable/native_transport_tests.cpp`（41 项断言）：

- 注册表的三态（未注册/已注册/注销），以及未注册时给出可读原因；
- 连接失败的完整错误路径（不存在的端口、状态转为 Error、10 秒内返回而不是
  卡到系统默认超时、未连接时 `send`/`pollOnce` 安全失败、重复 `close` 幂等）；
- **真起一个从站模拟器走 loopback socket**：发真实 Modbus TCP 请求、
  收响应、解帧、断言 HR[0..3] = 100/250/380/7，再发一条写请求并断言从站侧真的被写入；
- `DeviceManager::pump()` 把驱动请求转达到链路（用计数假链路）。

这组用例是**真 socket**，不是 mock —— 被测的正是 socket 行为本身。

## 与项目一的关系

项目一的 `TcpConnection` 用 epoll(ET) + 非阻塞 IO 手写缓冲区；
项目二的 Qt 链路交给 `QTcpSocket`，原生链路则回到 select + 阻塞 socket。
三者的判断依据都是同一句话：**事件来源应当与进程的驱动模型一致**。
项目一是纯事件循环，所以 epoll；项目二的界面在 Qt 事件循环里，所以信号槽；
项目二的 daemon 是自己写的主循环，所以 select 轮询。
