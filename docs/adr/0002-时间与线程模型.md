# ADR 0002：时间由外部驱动，设备层不持有线程

- 状态：接受
- 日期：2026-10-08

## 背景

采集网关天然需要两类时间行为：等待响应超时后的重传，以及周期性轮询。
最直接的写法是在设备类里起线程、用 `sleep` 或条件变量等待响应。
但这样会带来三个后果：超时逻辑难以精确测试（要真的等）、线程数量随设备数增长、
界面与采集线程之间必须加锁共享状态。

## 决策

设备层不创建线程，也不读取系统时间。所有时间行为通过一个入口驱动：

```cpp
void DeviceManager::tick(uint64_t nowMs);
```

- Qt 侧由 `QTimer`（建议 20~50ms）调用，传入单调递增的毫秒数；
- 测试侧由用例直接调用，构造「99ms 不超时、100ms 超时」这类边界；
- 响应到达由链路回调 `onBytes()` 触发，同样不阻塞。

设备会话内部只保存 `nowMs_`、`deadlineMs`、`nextPollAtMs`，`tick` 里做三件事：
判断超时、决定是否重传、决定是否发起下一次轮询。

## 理由

1. **可测**：超时与重传是项目二最容易被追问的逻辑，用假时钟可以在毫秒级精确断言；
2. **无线程**：N 台设备仍然只有调用方那一个定时器，不需要每台设备一个线程；
3. **无锁**：状态只在调用 tick 与 onBytes 的线程里改，界面通过回调拿到结果副本；
4. **可移植**：与 Qt 解耦之后，这套会话逻辑可以放进无界面网关，也可以被嵌入式侧复用。

## 代价

1. 轮询精度受调用间隔限制，最小分辨率等于 tick 周期；
2. 调用方必须保证 tick 被稳定调用，否则超时判定会被推迟；
3. 长耗时的处理（例如写数据库）不能放在 tick 里，否则会拖慢所有设备的调度。

## 与项目一的关系

项目一把最近到期时间交给 `epoll_wait` 当超时值，定时任务在事件循环线程里执行，同样没有额外线程。
两个项目的判断是一致的：**时间应当是外部输入，而不是某个组件内部自己等待**。
