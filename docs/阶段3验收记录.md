```
结果：全部通过
```

覆盖范围：

### 二、pymodbus 交叉验证（第三方实现）

```
断言 54 项，失败 0 项
结果：全部通过
```

为什么必须做这一步（实现指导原文）：

> 模拟器自己实现了错的字节序，把主站也带偏，所以一定要用第三方工具交叉验证。

自研主站 + 自研从站的闭环测试只能证明**两边理解一致**；若两边一起错，测试仍全绿。
pymodbus 3.15 是独立实现，它读出的值与配置一致，才能证明字节序真的是对的。

验证内容与结果：

| 项目 | 结果 |
| --- | --- |
| 读 HR[0..11]、HR[100]、HR[4]=65535 | 全部与配置一致 |
| 读 IR[0..2] | 全部与配置一致 |
| 读 COIL[0..11] | 全部与配置一致 |
| 读 DI[0..7] | 全部与配置一致 |
| 写 HR[20]=4321 并回读 | 成功 |
| 写 HR[30..33]=[11,22,33,44] 并回读 | 成功 |
| 写 COIL[5] ON/OFF 并回读 | 成功 |
| 写 COIL[40..43]=[T,F,T,T] 并回读 | 成功 |
| 读越界地址 200 | 返回异常，`exception_code=2`，`function_code=0x83` |
| 绕过客户端直接发「读 126 个」原始帧 | 从站回 `83 03`（数量超规范） |
| 单元号 9 请求（本从站为 1） | 从站一个字都不回，客户端表现为超时 |

其中「读 126 个」和「单元号不匹配」两项是**用原始 socket 手写帧**验证的：
pymodbus 客户端自己就会拒绝 `count > 125`，走它测不到从站的拒绝行为，
而现场真正的坏主站是会发出这种帧的。

## 观察到的一条重要现象

pymodbus 在客户端就挡掉了两类非法请求（`count > 125`、`count = 0`），
抛 `ValueError` 而不是发出去。这说明**规范上限是各家实现的共识**——
不只是本项目的自定约束。项目里对上限的判定（`kMaxReadRegisters = 125` 等）
与第三方一致，属于交叉印证。

## 未做的事（明确边界）

- **RTU 侧未验证**：模拟器目前只实现 TCP（`decodeRtu*` 与 RTU 组帧已有，但
  `SlaveSimulator` 没有串口链路），对应阶段 4。简历里不应写成「同时支持 RTU 与 TCP」。
- **Qt 界面未做**：`src/main.cpp` 仍是阶段 0 的空窗口，对应阶段 5。
- **异常注入引擎未做**：目前只能通过「请求非法」触发异常，
  主动制造坏 CRC / 断连 / 乱序的引擎属于阶段 8。

这三条与 README 的路线表一致。

## 复现命令

```bash
# 1) 不依赖 Qt 的构建与全部测试
./scripts/build_portable_tests.sh

# 2) 启动模拟器
./build_portable/slave_simulator config/slave-simulator.json

# 3) 另开一个终端做交叉验证
pip install pymodbus
python scripts/verify_simulator.py
```
