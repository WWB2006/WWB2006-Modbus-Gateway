## 三 覆盖的关键行为

| 行为 | 断言要点 |
| --- | --- |
| 正常读写 | 请求被接受、进入等待状态、响应取回 4 个寄存器、事务结束 |
| 超时与重传 | 99ms 不重传 / 100ms 重传；重传次数等于 retry 配置；达到上限后上报超时且只回调一次 |
| 坏 CRC | 整帧丢弃、错误计数为 1（不会逐字节重复计数）、不回调错误结果、继续等待 |
| 半包 | 只有半帧时不结束事务、缓冲保留、凑齐后解析成功 |
| 粘包 | 一次到达两帧，第一帧解出，第二帧因无在途事务计为迟到响应 |
| 事务号错配 | 错配响应被丢弃且不产生结果；超时重传后拿到正确结果 |
| 异常响应 | 不触发重传、计入响应与异常计数、错误信息为中文提示 |
| 单在途事务 | 在途期间第二个请求被拒绝，逻辑请求数仍为 1 |
| 自动轮询 | 到达轮询间隔才发起下一次，不会重叠 |
| 多设备管理 | 两台设备分别发起、结果回调带正确设备名、链路状态可查询 |
| 接收缓冲 | 追加、消费、读指针前移、越界清空 |

## 四 本阶段发现并修掉的问题

1. **回调没接线**：最初测试里只调用了 `setTransport()`，忘记把链路的字节回调转给会话，
   表现为「请求发出但永远没有响应」。修法是在会话上提供 `attach(TransportInterface&)`，
   把「设置链路」与「接管字节回调」合成一个动作，从 API 层面消除这类遗漏。
2. **同步回调导致的状态再入**：假链路如果在 `send()` 内部立刻回调，会在 `sendPending()`
   还没写完 `attempts`/`deadline` 时就把事务解掉。修法是**先更新状态再发送**，
   并把测试替身改成「入发件箱、由测试显式投递」，更贴近真实异步链路。
3. **坏 CRC 的重复计数**：最初按「丢 1 字节重新同步」处理，一个 9 字节的坏帧会被计数多次。
   改为由解码器返回推断帧长（`DecodeResult::frameLengthHint`），整帧丢弃，计数一次。
4. **悬空引用**：`DeviceManager::addDevice` 里原先把 `onState` 回调绑定到局部 `Entry` 的引用上，
   `push_back` 之后立即失效。改为用 `shared_ptr` 保存链路状态。

这四条都属于「只有真的把代码跑起来才会暴露」的问题，写进面试材料比背八股更有说服力。
